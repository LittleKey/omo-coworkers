## 1. 设计目标与核心原则

本方案面向扩展维护者与后续实现者，定义 OMO Coworkers 配置工作台的唯一权威信息架构、交互工作流、状态协议、数据所有权与技术边界。

1. **单权威配置与清晰状态分层**：扩展私有持久草稿是唯一可编辑的配置权威；用户编辑先在内存中试改，经显式保存落入私有草稿，再经显式预览发布规范化输出至全局 OMO 配置，不让两套并行的持久化配置互相竞争。
2. **极简信息架构与就近操作**：一级导航仅保留 **`角色`** 与 **`设置`**，删除名不副实的“项目设置”以及割裂心智模型的独立“方案”页；将“内置推荐配置”下沉为背景默认层，并在角色详情与模型选择当下提供直接控制。
3. **少文案、UI 优先、双端一体**：不在主界面暴露内部草稿修订号（如 `r12`）、双状态栏、冗余入口或长篇免责声明；通过徽标、紧凑差异清单与按需折叠区表达语义，同时兼容桌面端与手机端触控操作。
4. **诚实反映技术边界**：不将未接入能力（如自定义日志目录、运行态自动重载、外部 OpenCode 重启、未验证的一体化 OMO 运行时交付）伪装为可用控件或完成承诺。

## 2. 信息架构与响应式布局

### 2.1 一级导航与界面骨架

工作台仅设 **2 个一级导航**：**`角色`** | **`设置`**。顶栏右侧仅以紧凑徽标标注发布目标 **`全局 OMO`**，仅在需要重载或发生异常时追加轻量状态（如 `待重载`），平时保持干净。

```text
┌──────────────────────────────────────────────────────────┐
│ [角色]  设置                          全局 OMO · 待重载   │  ← 单行顶栏
├──────────────────────────────────────────────────────────┤
│ (条件横幅：平时完全隐藏；仅在 结果未知/外部冲突/推荐更新/校验报错 时出现) │
├─────────────────────┬────────────────────────────────────┤
│ [搜索角色]           │ designer  [已改]         [开关 ●] │
│                     │                                    │
│ orchestrator    🔒  │ 模型                     [恢复推荐] │
│  <已选模型>          │ ┌────────────────────────────────┐ │
│ ▸ designer      •   │ │ <provider>/<model>          ⌄  │ │
│  <已选模型>          │ └────────────────────────────────┘ │
│ oracle              │                                    │
│  <已选模型>          │ 思考等级                            │
│ observer        停  │ [默认] [low] [medium] [● high]     │
│  <已选模型>          │                                    │
│ claude        ACP   │ ▸ 内置指导与 Skills · 随发布同步    │
│  <已选包装模型>      │                                    │
├─────────────────────┴────────────────────────────────────┤
│ 未保存 · 2  [还原]                      [保存]  [保存并发布] │  ← 唯一状态与提交锚点
└──────────────────────────────────────────────────────────┘
```

### 2.2 响应式断点与无障碍规则

| 视口断点 | 布局结构与交互规则 |
| --- | --- |
| **桌面端（`>= 560px`）** | 左侧 `200px` 固定宽度平级角色列表（支持完整容纳 `document-writer` 等较长 ID 与右侧状态微标）+ 右侧角色详情区 + 底部固定状态操作栏。 |
| **手机端（`< 560px`）** | 1. 入口先展示全宽两行式**角色列表**（首行：角色 ID + 状态微标；次行：当前模型短名，支持全局一览）；<br>2. 点击角色进入全屏详情页（左上角提供明确返回 **`‹ 角色`**）；<br>3. 点击模型弹出**全屏模型选择器**（搜索框自动聚焦，字号 `>= 16px` 防止 iOS 自动缩放）；<br>4. 底部操作栏避开 `env(safe-area-inset-bottom)`，仅保留紧凑状态短标 + `保存` + `发布/保存并发布`。 |
| **通用可用性要求** | 交互控件最小触控区域 `44px`；长模型名允许换行或点击展开，不依赖桌面端悬停（hover）；所有状态图标与徽标均配备可访问名称（accessible name），关键状态不单纯依赖颜色区分。 |

### 2.3 精简文案规范

| 界面位置 | 规范文案 | 约束说明 |
| --- | --- | --- |
| 一级导航与目标 | `角色` / `设置` · `全局 OMO` | 不出现“方案”“项目设置”或内部修订号。 |
| 列表项微标 | `ACP` / `•`（已改）/ `!`（异常或未确认）/ `停` / `🔒` | 辅以无障碍文本标签；取消“个人覆盖”等重标签堆叠。 |
| 角色详情重置 | 模型字段同行操作：`恢复推荐` | 仅在启用内置推荐且当前角色偏离推荐值时显示。 |
| 底部状态区 | `未保存 · N` / `待发布 · N` / `发布中…` / `已同步` | 唯一状态与提交锚点，禁止顶栏与底栏重复播报草稿计数。 |
| 主操作按钮 | `还原` / `保存` / `发布 · N` / `保存并发布` | 按钮动词与是否先落草稿严格对应。 |
| 发布后运行态 | 顶栏徽标：`待重载` | 明确文件落盘不等于运行中实例已重载。 |
| 目录缓存提示 | 选择器内部：`Xm 前` / `更新中…` / `缓存 · 刷新失败` | 删除详情页冗余的外部目录跳转按钮。 |
| 异常状态横幅 | `发布结果未知` + 按钮 `查询状态` | 仅在异常时出现，不占用常态空间。 |

## 3. 角色体系、ACP 区分与内置推荐机制

### 3.1 平级角色列表与真实 ID

所有角色在 `角色` 列表中按真实配置 ID 平级呈现，不做意译，也不拆分独立的 ACP 一级页面。基于 `openchamber/native-config/schema/omo-3.0.8.json`、`openchamber/native-config/templates.mjs`、`openchamber/native-config/capabilities.mjs` 与 `openchamber/native-config/acp-settings.mjs`，工作台管理以下真实角色：

- **原生与协作核心角色**：`orchestrator`、`explorer`、`oracle`、`designer`、`fixer`、`observer`、`council`、`councillor`
- **扩展内置角色**：`document-writer`、`lark-operator`
- **外部 ACP 代理角色**：`claude`、`antigravity`

### 3.2 `disabled_agents` 与受保护角色语义

依据 OMO 3.0.8 Schema（`openchamber/native-config/schema/omo-3.0.8.json:1234-1240`、`42`、`openchamber/native-config/manager.mjs`）：

- **角色开关映射 `disabled_agents`**：`disabled_agents` 控制的是 **Agent（角色）是否实例化与可被委派**，而不是全局禁用某个模型。如后续需要屏蔽不常用的模型，应作为模型选择器内部的“隐藏/过滤列表”实现，严禁与 `disabled_agents` 混同。
- **受保护不可禁用角色**：`orchestrator` 与 `councillor` 在详情右上角显示只读锁标 `🔒`，不提供虚假启用/停用开关。
- **默认禁用角色**：`observer` 在 OMO 默认语义中处于禁用状态（未显式移出 `disabled_agents` 时视作停用）；启用时需配合视觉模型检查提示，不得隐式伪造配置。
- **内部协同角色**：`council` 与动态席位 `councillor-<seat>` 在详情中只读展示当前配置生成的席位结构与对 `councillor` 的依赖说明，避免孤立开关引发配置歧义。

### 3.3 普通角色与 ACP 角色详情设计

| 字段/区块 | 普通与扩展角色 | ACP 角色（`claude`、`antigravity`） |
| --- | --- | --- |
| **角色启用** | 开关控制（`orchestrator`/`councillor` 锁定只读） | 列表带 `ACP` 微标；开关映射 `disabled_agents` 成员状态 |
| **模型选择** | 字段名：`模型`（对应 `agents.<id>.model`） | 字段名明确标为：**`包装层模型`**（`acpAgents.<id>.wrapperModel`，严禁与外部代理内部模型混淆） |
| **内部模型** | 不适用 | 单行只读说明：**`内部模型：由外部代理运行时决定`**，不设伪下拉选择框 |
| **思考等级** | `思考等级`（`variant`）：<=4 项用横向分段按钮，>4 项退回下拉；未知值带 `?` 标记原样保留 | 归属于包装层模型可用选项；不伪装控制内部推理深度 |
| **连接参数** | 不适用 | **`连接参数`（默认折叠）**：折叠行显示摘要（如 `command · permissionMode · timeoutMs`），展开为 2 列紧凑表单：`command`、`args`（JSON）、`cwd`、`permissionMode`、`timeoutMs` |
| **行为选项** | 若无专属环境项则省略 | **`行为选项`（默认折叠）**：收纳 `claude` 专属环境开关（`CLAUDE_CODE_DISABLE_CLAUDE_MDS`、`CLAUDE_CODE_DISABLE_BUNDLED_SKILLS`、`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`）及现有 `claudeGuard` 开关，不丢失 `v7.1.2` 已有能力 |
| **内置指导** | **`内置指导与 Skills`（默认折叠）** | 同左，展示扩展随发布同步的只读指导来源与摘要（整合自原“项目设置”的 `collaboration` 等指导信息） |

### 3.4 “内置推荐配置”的定位与生命周期

扩展提供**唯一一套内置推荐配置**作为专家默认配置层（Default Layer），通过“两处融入 + 一处总控”服务用户，而非抽象的“方案管理”：

1. **角色详情页（按需还原）**：当启用内置推荐且当前角色模型或思考等级与推荐值不同时，列表项亮蓝点 `•`，详情页模型标签右侧出现 **`恢复推荐`** 按钮，一键将该角色恢复为推荐值（写入内存编辑态）。
2. **模型选择器（决策点引导）**：打开任一角色的模型选择器时，顶部置顶 **`★ 推荐`** 分组，展示该角色推荐模型及可折叠的一行角色定位说明（如分工偏好）；若推荐模型不在当前可用目录中，则灰显标示 `目录中未找到`，不强行写入不可用模型。
3. **设置页第一组（全局开关与总览）**：
   - **`使用内置推荐`（默认开启）**：
     - **开启状态下升级扩展**：若新版内置推荐有变化，在 `角色` 页顶部弹出一次性轻量横幅 **`内置推荐已更新 · 影响 N 个角色 [查看并应用] [忽略]`**；应用时**保留用户的个人单角色覆盖**，且**绝不自动发布**。
     - **关闭（Opt-out）时**：**立即将所有角色当前有效配置固化为纯手动配置**（保留当前已选模型、思考等级与启停状态，绝不重置或丢失）；之后不再跟随推荐升级，角色页隐藏 `恢复推荐` 按钮。
   - **`查看推荐配比`**：可折叠只读紧凑表（角色 ID → 推荐模型/等级 → 分工简注），供用户随时核对完整推荐内容。
   - **`全部恢复推荐`**：一次性清除个人覆盖并将草稿恢复为推荐基线（仍需用户显式保存与发布）。
4. **原生 OMO 输出语义**：发布时，扩展根据“内置推荐 + 个人覆盖”计算**最终有效配置**，规范化写入全局 OMO 配置文件，不在原生文件中残留两套互相冲突的活动 preset。

## 4. 核心工作流与状态协议

> **【规则优先级提示 · 已由第 9.1 节部分替代】**  
> 本节第 4.1–4.2 节保留了首版“显式 `保存` 按钮 + 所有全局写入均须通过 `发布`”的初始设计历史。依据 **2026-11-27 补充决定（见第 9.1 节）**，以下两项已正式替代旧规则：① 放弃独立显式 `保存` 按钮，改为**每次有效编辑自动保存至扩展私有持久草稿**；② 引入 OMO `liveConfigRefresh` 分级生效——**已验证可热刷新的变更通过 `保存生效` 直接投影写入原生配置，仅不可热刷新的冷变更仍须走显式 `发布` 流程**。第 4.3 节的分层确认边界、事务锁、外部冲突检测与 `发布结果未知` 恢复协议继续保持有效。

### 4.1 四层状态模型与首版保存/发布约定

工作台底层维护四个严格分离的状态概念，但对用户只暴露最小必要反馈：

| 层级 | 语义与持久性 | 界面表现与约束 |
| --- | --- | --- |
| **1. 内存编辑态** | 当前页面中的试改内容，切换角色不丢失，允许暂不完整（如暂未选模型）。 | 底栏显示 `未保存 · N`，提供 `还原` 一键丢弃未保存编辑；关闭或离开页面前提示拦截。 |
| **2. 扩展持久草稿** | 扩展私有目录中的**唯一权威期望配置**（包含内置推荐启用状态与版本、个人覆盖、各角色配置及扩展设置、格式版本与单调修订号）。 | 仅用户点击 `保存` 或确认 `保存并发布` 时写入。**允许保存尚不完整的草稿，严格运行校验推迟到发布阶段。** |
| **3. 已发布凭据** | 记录已发布草稿的修订号、目标路径、`operationId`、内容摘要与备份引用。 | 仅作为发布凭证与事务恢复依据，**不是**第二份可编辑配置来源。 |
| **4. 运行态观察** | 独立追踪配置是否已由宿主加载生效。 | 发布写盘成功后顶栏仅显示 **`待重载`**，不将“写盘成功”等同于“运行态已生效”。 |

> **关于显式 `保存` + `发布` 的首版决策说明**：  
> 首版默认采用显式 **`保存`** 与 **`发布`** 双动作，核心依据如下：① 用户可在内存中连续试改多个角色配比并通过 `还原` 随时回退，避免未完成或试验性输入污染持久草稿；② 与“打开发布预览弹窗无副作用”协议天然一致，消除误触即落盘的风险。此外，“每次编辑自动保存草稿（底栏仅留 `还原草稿` + `发布`）”作为备选交互仍记入第 9 节未决事项，待后续交互确认后再决定是否演进。

### 4.2 底栏四态切换与无副作用预览

1. **内存有未保存修改**：底栏左 `未保存 · N` + `[还原]`；右 `[保存]`（亮态）+ `[保存并发布]`（主按钮）。
2. **草稿已保存、未发布**：底栏左 `待发布 · N`；右 `[保存]`（置灰）+ `[发布 · N]`（主按钮）。
3. **发布执行中**：锁定当前已保存草稿的修订号在后台执行发布，**允许用户继续在内存中编辑下一版**，后台迟到响应不得覆盖或清空用户新编辑；底栏显示 `发布中…` 并禁用重复点击发布。
4. **发布预览弹窗的副作用隔离**：
   - 点击 `发布` 或 `保存并发布` 仅计算差异并打开预览弹窗，**绝不在打开或取消弹窗时静默执行保存或修改草稿状态**。
   - 弹窗主体必须展示**真实字段级变更清单（Diff）**（例如：`designer: 模型 A → 模型 B`、`observer: 停用 → 启用`），而非笼统分类或静态长篇免责墙。
   - 弹窗底部仅保留 1 行边界说明：`仅覆盖扩展托管项，保留其余配置与 opencode.json`。

### 4.3 分层确认边界与异常恢复协议

- **常规发布（单次确认）**：仅修改普通托管角色的模型、思考等级、启停或引导开关且无冲突时，不强制要求勾选确认框，查看差异后一键点击 `确认发布`（或 `保存并发布`）即可。
- **高风险与冲突发布（强制显式勾选）**：仅当触发以下任一条件时，高亮风险区块并要求勾选确认：
  1. **首次接管既有外部配置**（将已有非扩展托管的配置纳入扩展管理，且仅在原生配置可安全解析时允许接管；复杂未知继承关系直接阻止静默压平）；
  2. **检测到外部手动修改将被覆盖**（自上次发布后全局文件被外部工具改动：弹窗中必须同屏提供 **`导入外部修改`** 选项）；
  3. **ACP 高危运行变更**（修改 ACP 代理 `command` 可执行程序或将 `permissionMode` 设为 `allow`）。
- **超时与响应丢失恢复（`发布结果未知`）**：
  - 提交前生成持久 `operationId` 并先落盘 `pending` 事务记录与必要备份（可参考现有 `openchamber/native-config/recipe-state.mjs:105-229` 的锁与读回框架，替换掉会随预览消耗或 5 分钟过期的短寿命内存快照 `openchamber/native-config/manager.mjs:242-251`）。
  - 发生超时、连接中断或写后读回失败时，**严禁自动重试或盲写**；顶部异常横幅常驻 **`发布结果未知`** + **`[查询状态]`**，同时禁用 `发布` 防止并发覆写。
  - 点击 `查询状态` 通过持久 `operationId` 核对落盘记录与最新目标文件读回摘要；若恢复期间发现第三方并发修改，必须停止自动回滚并交由用户处置。

## 5. 模型目录解析与磁盘 SWR 缓存

### 5.1 多段模型 ID 与兼容保留规则

针对 `openchamber/service/model-catalog.mjs` 暴露的历史问题，确立以下模型目录与引用契约：

- **三段及多段模型 ID 保留**：完整模型标识按不透明的 `{providerID, id, variant}` 结构处理，允许 `id` 中包含多个 `/`（如 `magpie/<provider>/<model>`），严禁仅取首尾两段截断。
- **`id` 与 `modelID` 匹配修正**：在关联模型列表与 `variants`（思考等级）能力时，必须兼容 OpenCode 目录字段中别名 `id` 与上游 `modelID` 不一致的场景，避免丢失 `variants` 等级（现行 `openchamber/service/model-catalog.mjs:80-88` 仅以 `providerID + '/' + modelID` 匹配存在丢等级风险）。
- **未知引用与未知等级保护**：当前草稿或已有配置中若存在目录里未检索到的模型 ID 或未知 `variant`，工作台必须**原样保留该值**并标注 `!` / `?` 提示“目录中未找到”或“未确认”，绝不自动清空或悄悄替换为默认模型。

### 5.2 磁盘 SWR（Stale-While-Revalidate）缓存策略

- **零等待渲染与静默刷新**：打开工作台面板或打开模型选择器时，立即从扩展私有磁盘缓存渲染列表；同时后台触发异步刷新（同一上下文的并发在途请求自动合并，短冷却窗口内去重）；手动点击刷新则跳过新鲜期并合并在途请求。
- **失败降级规则**：刷新超时或失败时，**绝不清空既有缓存或当前已选模型**，仅在选择器搜索框旁以紧凑小字显示 `缓存 · 刷新失败` 及重试图标；当磁盘无任何缓存且刷新失败时，明确提示“未获取目录”，不能伪装成“可用模型列表为空”。
- **严格隔离与白名单字段**：
  - 缓存键必须隔离以下维度：**目标实例身份（`targetIdentity`）**、**配置作用域（`configScope`）**、**OpenCode / API 格式版本**、**provider 配置世代**。无法确认目标身份时，不复用其他实例缓存；模型主体与 `variants` 获取状态独立记录。
  - 仅落盘白名单字段：`providerID`、`id`、显示名称、`variants`、必要能力标记、数据来源标记与获取时间戳；**严禁缓存任何请求 headers、上游凭据、token 或完整原始 HTTP 响应**。

### 5.3 目录数据来源边界（关键约束）

- **现状事实**：现行 `openchamber/service/model-catalog.mjs:52-118` 仅依赖服务进程 `PATH` 中的 `opencode models` 与 `opencode api GET /api/model`，未绑定当前运行中的外部 OpenCode 实例，且在报错时通过 `caches.delete(key)`（第 103 行）直接清除了旧缓存。
- **SDK 限制事实**：依据 `@openchamber/sdk@2.8.1` 的 `GUEST_SERVICES.md:671-684`，公开 `opencode` 只读代理仅放行 `/api/session*`、`/api/project` 与 `/api/event`，其余路由（含 `/api/model`）均返回 `403 NOT_A_LISTED_READ`。
- **设计约束**：后续正式实现应优先走**绑定当前目标的受授权结构化模型接口**；在宿主正式通道未打通前，任何来自 CLI 的结果必须显式标注来源为 CLI 兜底，不得假装其与当前连接的目标实例绝对一致，更不允许抓取宿主私有接口、扫描端口或私自拉起新 OpenCode 进程。

## 6. 数据所有权、`设置` 页设计及运维边界

### 6.1 固定配置所有权与单向导入

- **固定权责规则**：工作台取消多套相互矛盾的合并/覆盖开关，采用唯一固定规则——**托管角色的受控字段与启停状态由扩展发布结果为准，非托管字段及 `opencode.json` 原样保留**。
- **单向与显式导入**：不存在后台定时循环或静默抢写机制。当用户在工作台之外手动改写了全局 OMO 配置时，扩展在读取阶段识别外部变更并在发布或列表顶部提示冲突，由用户显式选择 **`导入外部修改`** 或确认覆盖。

### 6.2 `设置` 页分组设计（零假控件）

`设置` 页严格精简为以下 **4 个分组**，所有控件均对应真实可落地边界：

1. **内置推荐**
   - `使用内置推荐` 开关（默认开；关闭时固化当前有效配置为手动模式）。
   - `查看推荐配比` 折叠只读表。
   - `全部恢复推荐` 按钮（仅重置草稿，不直接发布）。
2. **发布与生效**
   - `允许写入全局配置` 开关（默认开；关闭后进入只读演练与导出模式，仍可编辑、保存草稿、预览差异与导出，但禁止写全局文件）。
   - `发布后自动重载` 开关：**当前明确置灰禁用**，并在旁注 1 行诚实说明：`当前 OpenChamber SDK (2.8.1) 未提供公开重载或重启接口，外部 OpenCode 服务需自行重载`。
   - 固定规则 1 行摘要：`托管角色以扩展为准，其余配置与 opencode.json 原样保留`。
3. **诊断日志**
   - `诊断日志` 开关：**默认关闭**，开启后带有 **30 分钟自动到期关闭**机制。
   - 记录范围：仅记录操作编号（`operationId`）、阶段、耗时、修订号与错误码；**严禁记录提示词、完整配置正文、环境变量或任何凭据/令牌**。与持久发布的恢复日志（WAL）严格隔离，关闭诊断日志绝不影响事务恢复能力。
   - `日志目录`：仅**只读**展示当前真实可用的扩展私有目录（`OPENCHAMBER_SERVICE_DATA_DIR` 下的 `logs/`），在未接入宿主目录授权接口前**不提供假可选项或伪自定义路径选择器**。
   - 提供 `导出日志` 与 `清空日志` 操作。
4. **数据与环境（默认折叠）**
   - `导出配置` / `导入配置`：导出扩展私有草稿与个人覆盖备份。界面需明确提示：**卸载扩展会删除扩展私有数据目录（`OPENCHAMBER_SERVICE_DATA_DIR`，见 SDK 2.8.1 契约）；仅备份 `opencode.json` 无法保留在扩展内做的个性化覆盖**。
   - `从全局 OMO 导入`：显式读取当前全局 OMO 文件并导入为可编辑草稿。
   - 只读状态显示：当前目标全局配置文件路径，以及 **OMO 一体化运行时交付状态（当前诚实标明为“未完整接入/待验证”，不可伪称装完扩展即具备完整 OMO 运行时）**。

### 6.3 卸载、备份与无悬空资产约束

- 扩展卸载时不得默认静默回滚用户原生的全局配置，但必须提供**显式停止托管**与**带冲突检查的可选回退/导出**指引。
- 扩展写入全局配置文件的任何字段或引用路径，**禁止指向卸载后会被删除的扩展私有数据目录**（如把提示词路径硬指向扩展数据区），确保卸载扩展后不会在用户全局配置中留下破坏 OpenCode 启动的悬空资产引用。

## 7. 重点验收标准（Acceptance Criteria）

1. **信息架构与文案**：仅存在 `角色` 与 `设置` 两个一级导航；主界面无独立 `方案` 页或 `项目设置` 页；不显示 `r12` 内部版本号；顶栏与底栏无重复状态播报；无未接入能力的假可选项。
2. **角色体系与 ACP 区分**：12 个真实角色 ID 平级展示；`orchestrator`/`councillor` 无法被界面停用；`observer` 默认停用语义准确；`claude`/`antigravity` 在详情内明确区分 `包装层模型` 与只读 `内部模型`、`连接参数` 与 `行为选项` 默认折叠且摘要准确、`v7.1.2` 原有 `behaviorEnv` 与 `claudeGuard` 完整保留。
3. **内置推荐与退出固化**：可在角色页一键 `恢复推荐`、在选择器置顶查看 `★ 推荐`、在设置页展开只读配比表；关闭 `使用内置推荐` 后立即保留当前所有角色有效配置不丢失；升级推荐仅弹预览横幅保留个人覆盖且不自动发布。
4. **无副作用预览与连续编辑恢复**：打开/取消发布预览不改变内存草稿、不落盘保存；发布进行中允许继续内存编辑且不被迟到响应覆盖；常规发布单次确认并展示真实字段 Diff；首次接管、外部冲突及 ACP 高危变更触发勾选确认并提供 `导入外部修改`；响应超时/读回失败展示 `发布结果未知` 与 `查询状态` 并锁定并发发布。
5. **模型目录与磁盘 SWR**：支持含多 `/` 的模型 ID 与别名 `id` 对应 `variants`；离线/刷新失败时保留既有缓存与当前已选值并标示状态，不清空列表；不同目标实例/作用域间缓存隔离，缓存文件不含敏感请求头或凭据。
6. **双端与无障碍**：`>= 560px` 与 `< 560px` 断点布局、全屏模型选择器（`16px` 输入框）、安全区底栏、44px 触控尺寸、键盘导航与屏幕阅读器可访问标签均验证通过。

以下能力明确排除在当前版本设计范围之外：

4. **“只装扩展即拥有完整 OMO”交付闭环（未验证）**：当前 `openchamber/plugin/index.mjs:1-13` 仅组合扩展自有插件（`claudeAdvisor` 与 `setupWriterRole`），`package.json` 未包含完整 OMO 运行组件；后续若要实现一体化交付，需专项验证固定兼容版本 OMO 的打包方式、与外部独立 OMO 的去重注册机制及外部 OpenCode 实例的插件注入边界。

   - **SDK 约束与待验证项**：依据 `@openchamber/sdk@2.8.1`（`GUEST_SERVICES.md:671-684`、`API.md:580`），公开 `opencode` 只读代理仍不放行 `/api/model`（返回 `403 NOT_A_LISTED_READ`），且当宿主管理配置未覆盖外部 OpenCode 时，`opencodePlugin` 仍需用户通过扩展页面 **Add to global config** 显式注册至外部全局配置。因此，OpenCode 进程内插件向扩展 `service` / `panel` 回传目录数据的**受授权、版本化、目标身份绑定桥接通道**仍属于实施前必须完成协议设计与验证的前置缺口；严禁抓取宿主私有接口、扫描端口或私自启动新 OpenCode 进程。

3. **使用 `liveConfigRefresh` 区分“保存生效”与“发布”（对应原第 9 节第 3 项，部分替代第 1、4.1–4.2 节）**
   - **机制关键澄清**：依据 `openchamber/native-config/schema/omo-3.0.8.json:49-52`，`liveConfigRefresh` 是 OMO 插件对**原生全局 OMO 配置文件**的文件监听开关（仅在存在 `session-preset`、`sidebar` 或 `retry` 消费者时构建 watcher，说明载明其重载 model/preset profiles）。**仅写入扩展私有草稿不会触发 `liveConfigRefresh`，也不会更新运行态。**
   - **分级写入与操作语义（供原型与实现遵循）**：
     - **热更新动作（`保存生效`）**：当待应用变更**全部属于已验证可由 `liveConfigRefresh` 热刷新的字段**时，用户点击底栏 **`保存生效`**，扩展在 `允许写入全局配置` 开启前提下（并经过第 4.3 节文件锁与外部修改冲突校验），**只将已验证的热字段投影写入原生全局 OMO 配置文件**，以触发 `liveConfigRefresh` 并保留 `运行态观察` 标记（仅当宿主/插件可观测刷新完成时标记生效，否则保持待确认提示，不虚报已生效）。
     - **冷变更动作（`发布 · N`）**：凡涉及新增/删除/启停角色（`disabled_agents`）、ACP 连接与权限（`command`/`args`/`cwd`/`permissionMode`/`timeoutMs`）、首次接管、外部冲突覆盖或高危变更，**仍必须走第 4.2–4.3 节定义的无副作用预览弹窗与分层确认流程**，写盘后顶栏轻标 **`待重载`**。
     - **混合变更与 Fail-Closed 原则**：当草稿同时包含热字段与冷字段时，**严禁在热更新投影中夹带未确认的冷字段**；系统可仅将已确认的热字段写入原生文件，其余冷变更继续留在草稿待发布队列，底栏保留 **`发布 · N`**（`N` 仅计入未发布的冷变更数量）。在外部 OpenCode + OMO `3.0.8` 环境下完成实证矩阵前，所有未获验证的字段均按**冷变更（fail-closed）**处理；不承诺全局一键热重载，也不声称 ACP 支持热刷新。

4. **不打包 `oh-my-opencode-slim` 插件，由 `dotfiles/opencode.json` 预置（对应原第 9 节第 4 项及第 6.2 节第 4 组）**
   - **范围删减决定**：正式取消“通过单一扩展打包或安装完整 `oh-my-opencode-slim` 运行时”的规划目标。`openchamber/plugin/index.mjs:1-13` 仅承载扩展自身行为插件（`claudeAdvisor`、`setupWriterRole` 及后续目录辅助），不捆绑、不分发、也不自动向 `opencode.json` 注入第三方 OMO 插件。
   - **清晰职责分工**：用户通过个人 `dotfiles` 与 `opencode.json` 预置 OMO 插件本体、运行依赖与 provider 配置；本扩展专注于 OMO 角色/参数配置管理，并在启动与 `设置 -> 数据与环境` 中提供**只读前置依赖诊断**（例如提示未检测到目标 OMO 配置或插件依赖缺失并指引核对 `opencode.json`，但不越权执行安装或修改 `opencode.json`）。第 6.3 节关于卸载提醒与**禁止在全局配置写入指向扩展私有数据目录的悬空路径**之约束继续严格有效。

5. **采纳每次编辑自动保存扩展私有草稿（对应原第 9 节第 5 项，替代第 2.1、2.3、4.1、4.2 节显式 `保存` 按钮）**
   - **交互与持久化契约**：工作台取消独立显式 `保存` 按钮，改为**每次有效编辑自动持久化至扩展私有草稿**（采用防抖写入、单调递增修订号与并发隔离，**严禁每次按键直接写入全局原生 OMO 文件**）。
   - **更新后的底栏状态与按钮设计（供 Designer 更新原型）**：
     - 状态反馈收敛为轻量自动保存提示（如 `已自动保存` / `正在保存草稿…` / `草稿保存失败`）与 **`还原草稿`** 按钮（丢弃尚未生效/尚未发布的草稿改动，附轻量确认防误触）；
     - 主动作按钮随变更类别动态收敛为单主钮：
       1. 无待生效/待发布变更：底栏仅显示 `已同步`（无多余主按钮）；
       2. 仅含已验证热刷新变更：显示 **`还原草稿`** + **`保存生效`**；
       3. 含冷变更或热/冷混合变更：显示 **`还原草稿`** + **`发布 · N`**（进入无副作用差异预览弹窗；若存在未写出的热变更，可一并纳入本次发布并明确区分“可热生效项”与“需重载项”）；
     - 写入或发布执行期间，后台锁定当前目标修订号并禁用重复提交，同时**允许用户继续编辑并自动写入下一修订号私有草稿**，后台迟到响应不得覆盖或清空新编辑；写盘包含冷变更后顶栏继续以 **`待重载`** 提示。
