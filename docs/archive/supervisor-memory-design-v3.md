# Supervisor Memory 设计 v3.1 — 运行时候选 + 人审规则 + 确定性执行

日期: 2026-10-22
状态: 草案(门 A/B 未冻结; 待检查-0 分组数据)
评审链: 用户九点运行时原案 → Oracle R16 REJECT-as-is + 收窄方向 → v3.0 → Claude R17 proceed-with-changes(三处修正+统计修正,已并入) → v3.1
前任: v2.0 静态受管段落(归档 `docs/archive/supervisor-memory-design-v2.md`, 保留为基线与回退臂)

## 0. 一句话与演进

**主模型在会话中经专用工具登记"问题"与"复发事件"(机器管发现), 用户批准后成为规则(人管判断), 规则经确定性通道注入执行, 效果只由真实用户纠正校验(外部反馈)。**

演进: v2.0 静态路线(纠正→批准→AGENTS.md 段落)成立但被动; 用户提出九点运行时闭环原案(问题存储/事件关联/自动修正/概率 nudge/退化/自动刷新); Oracle R16 判定原案不能直接实施——缺审批、全量注入违预算、概率无统计基础、自报自评自嗨循环风险——但运行时观察方向保留, 收窄为本设计。

核心问题不变: **降低同类纠错的复发, 降低人工维护成本。** "记录了问题"与"关联了旧问题"都不是"防复发", 只有"用户再次纠正之前识别并改正"才是。

## 1. 设计思想

1. **机制 + 数据 + 外部校验**: 系统靠数据持续运转, 但效果只能由真实用户纠正(外部信号)校验——模型自报、计数升高、注入命中率都不是效果证据。
2. **机器管发现, 人管判断**(自 v1 系不变): 模型可写候选与事件; **只有用户能让规则生效、停用或重新启用**。
3. **候选 ≠ 发生 ≠ 生效**: "希望观测"(Issue 候选)、"确实发生"(Event)、"允许注入"(Rule)三者分离; 愿望不进发生次数, 事件不自动变规则。
4. **热路径零智能**: 注入只执行已批准的确定性规则, 复用 nudge 单出口与预算(≤3 次/会话, ≤1200 字符)。
5. **反自嗨回路**: 注入的问题列表本身就是记忆注入——被提醒后模型"更容易看见"该主题, 上报上升不等于问题变多; 一切以用户纠正为准。
6. **fail-closed + 一切可见**: 工具写失败即跳过; 每次登记/跳过/注入一行日志; 总开关可停。
7. **follow 上游**: 不动官方 prompt/skills; 新增仅两个工具描述与 supervisor 自有存储。

## 2. 对象模型(三概念, 非三张关系表的强制)

| 对象 | 含义 | 谁写 | 状态 |
|---|---|---|---|
| **Issue(问题候选)** | 需要关注什么: 一行描述 + 主题(导航用) + 创建证据 | 工具(候选) / 用户 | draft → approved → merged/dropped |
| **Event(事件)** | 何时、依据哪条真实证据再次发生 | 工具(候选, 幂等) | 待确认 → 确认 / 误报 |
| **Rule(已批准规则)** | 允许给模型什么提醒: 一行规则文本 + 适用范围 + 注入方式 | **仅用户批准** | active → disabled(停用需人, 重启需人) |

- 存储: 服务端 supervisor 自有数据区(`~/.local/share/opencode/storage/plugin/supervisor/memory/`, JSONL 即可; 量级 52 纠正/8 周, 不需要关系数据库)。不放进工作仓库。
- **宿主赋值, 不信模型传参**: project/session/agent 由 hook 上下文注入, 模型参数仅作描述性字段。
- 主题(必填)只作导航聚类, **不代表问题身份**; 去重与合并由用户在周度复核中处理(无 pending-merge 自动状态, R17: 6.5 条/周量级下周度人工聚类是分钟级工作)。
- 同一来源事件**幂等**: 重试/重复调用不累计次数。
- **证据来源宿主强制**(R17): evidence 引用必须是同项目内真实存在的用户消息 ID, 宿主直接拒绝其他一切来源——伪造来源与跨项目关联在结构上不可能, 不再依赖模型自觉或事后抽查。

## 3. 工具面(合并为一个上报工具, R17)

1. `report_correction`(R17 合并原 report_issue/report_event): 上报一次用户纠正。参数: 描述/主题/evidence(真实用户消息引用, 宿主校验)/可选 issueId(宿主确认过存在且同项目时, 本次记为该 issue 的复发事件; 无 issueId 则新建 issue 候选)。**返回仅 ack + ID, 不返回任何历史**——未批准的记忆不得经工具返回进入任务上下文(R17: 这正是 R16 警告的自嗨回路入口)。
2. `query_memory`(无副作用查询): 只返回**已批准 Rule** 与目录级 issue 摘要, 不返回未批准候选详情。
- 工具描述明确: 允许不记录; **禁止**把模型自评、工具返回、nudge 内容当作用户纠正; 无有效 evidence → 宿主直接拒绝调用。
- 工具对根会话可见; **首版拒绝子会话来源**(宿主拒绝写入, 防根/子重复计数)。
- mock 回执支持(验证期不写生产存储)。

## 4. 触发流(report_correction 之后发生什么)

```
report_correction(幂等, 宿主校验 evidence)
  → ① 新建 Issue 候选 或 追加 Event + 关联计数(仅此为自动)
  → ② 返回 ack + ID(无历史, 无注入)
  → ③ 规则文本起草发生在周度复核时(人审界面), 不在任务会话内注入草稿(R17)
  → ④ 用户复核: 合并/丢弃/批准 → Rule 生效
  无任何环节自动改 Rule 状态; 无旁路模型链(不派第二个模型)
```

- 停用/否决优先: 用户停用的规则, 事件再多次也不复活(否决点 9 的自动刷新)。
- 刷新=事件追加+请求复核, 由用户决定; 不存在"消失→复发→自动刷新"通道(防刷新震荡)。

## 5. 注入(执行已批准规则)

- 复用 supervisor nudge 单出口: ≤3 次/会话、≤1200 字符、合成 user 消息、单条合并。
- **注入方式两案, 由门 B 裁决**: a) 静态常驻(规则文本小, 直接随 context); b) 目录+按需读取(只注入一行目录, 模型 query_memory 取详情)。
- 记录 planned vs delivered; delivered 才算送达。
- 新问题若明显由提醒诱发 → 计入该规则的负面结果, 不因"难关联"排除(否决原案点 7 的信息丢弃)。

## 6. 效果评估(只有外部信号算数)

- 主指标: **用户再纠正窗口数**(同类行为被用户再次纠正)。
- 记录: 每 issue 的事件计数/每 rule 的注入次数与 delivered/再纠正窗口关联(人工在待审列表点选, 非自动图谱)。
- 模型自报不算效果; 计数上升不算效果; 注入命中不算效果。
- 初版**无概率退化公式**(原案点 8 搁置): 只有启用/停用 + 试运行结束统一复核。同会话连续注入、跨会话降频等留待有数据后按实测定。

## 7. 验证门(检查-0 → 门 A → 门 B; 门 A/B 未冻结, 检查-0 进行中)

### 检查-0(先行, 无需代码, 决定门 A/B 是否存在) — R17 → 已完成

对 52 条历史纠正**按底层问题人工分组**(粒度=一条规则能否同时覆盖), 统计每组: 大小/是否跨会话复发/间隔天数/项目。报告: `/tmp/opencode/memory-lookback/grouping.md`。
**预登记判定: 跨会话复发组数 X < 5 → 跳过门 A/B, 产品定为 v2.0 静态 + 手动"记住这次纠正"入口; X ≥ 5 → 门 A/B 可行。**
**结果(2026-10-22): X = 10(G-A…G-J, 全部有不同 sessionId 确切证据, 无一依赖 B 类主题链; 剔除最弱组后 X=7 判定不变) → 门 A/B 可行。** 21 组=11 规则组+10 无复发单例; 跨会话组总实例 41 条/8 周 ≈5.1 条/周 → 试运行 6 周可观测 ~30 候选; 头部组 A/B/C/D 单组 8 周可评估, 尾部组(E/I 2 例)需 ≥12 周或并组; G-E/H/I 集中于 opencode-bcp 单目录 → 规则范围须含 project/directory 维度。**主表按行判复发系统性低估组级复发**(G-H 三行各自"无复发", 归组后显 18 天 3 会话模式)。
依据: 最高杠杆假设不是"模型能否记录"(门 A 可验), 而是**"纠正是否跨会话复发得足够频繁, 让任何规则有触发机会"**——检查-0 已证实。

### 门 A: 主模型能否可靠"被纠正后主动记录"

- 数据: 52 条真实纠正分开发集(~12)/盲测集(~40); 另 300 条非纠正(随机 + 边界: 普通需求/引用他人纠正/工具报错/模型自评/合成 nudge; 合成边界案例**单独报告**, 不与真实非纠正混算, R17)。
- 条件: 真实部署的主模型+官方 prompt+完整工具列表, 仅新增工具描述; mock 写入; 模型自然续写, **不得追问"你是否应该记录"**; 关联测试只提供事件当时已存在的 issue。
- 通过线: 记录召回 ≥80%(注: 40 条下 95% CI 约 65-89%, 结论按区间读, R17); 关联准确 ≥90%(仅当关联对样本 ≥ 检查-0 给出的量, 否则此指标无意义); 非纠正误报 ≤3/300(R17 修订: 候选误报代价=审阅时间非伤害, 配套指标=预期周审阅负担; 0/300 只说明比率 <1%); 伪造来源/跨项目关联已由宿主强制消除, 不再列为检查项(R17); 不允许二次催促补漏。
- **封盲纪律(R17)**: 盲测 40 条必须在工具描述撰写之前封存——设计者已读过 replay-27 全部语料; 负例取自相同会话分布。
- 失败处理: 可改工具描述后重留盲测集, 不得调到原测试集通过。**门 A 失败 → 放弃自动记录, 退回 v2.0 静态 + 手动入口。**

### 门 B: 运行时路线是否优于简单人审规则

- **三臂**成对比较(R17 修订, 新增无记忆臂): 无记忆空白 / 人审规则静态加载(v2.0 形态) / 目录+按需读取·运行时发现(遵守额度)。同知识内容。
- 复用 replay-27 的错误前窗口; 冻结规则/工具描述/评分标准/**判定者与窗口长度**(R17)后运行; 运行时组不得被告知"本例该用哪条规则"; 每窗口 **≥3 次采样**(R17: 单样本 5-0 分裂 p≈0.06, 8-3 p≈0.23, 无重复采样时"净减 ≥5"是噪声)。
- 记录: 再纠正窗口数/新增其他错误/额外输入与调用与维护成本; 规则取自已知错误的反事实回放须标注(两臂同膨胀, 不作臂间差异依据, R17)。
- 通过线(工程门槛非统计声明): 运行时组相对静态组净减 ≥5 个再纠正窗口且无新增严重错误, 且静态组相对空白臂有可见收益(否则连静态规则都不该上, R17), 成本 ≤ 约定上限。
- 限制: 无环境快照时最多验证识别与选择, "模型说会改"不计修复。
- 门 B 通过后还需真实影子运行; **时长由检查-0 的组复发率决定**(R17: 2 周仅 ~13 次纠正、2-4 次触发机会, 默认无结论); **无适用机会则无效果结论**。
