# Part I. 总体方向契约(R19, 经 R21 存储与作用域修订)

**方向判定：PASS；这是分阶段建设的方向契约，不是收益证明或上线验收。**
**一句话：系统替用户收集纠正、整理经验；用户决定记住什么、在哪里生效，真实使用决定是否值得保留。**

## I.1 契约范围与当前依据

- 核心目标是减少同类纠错和人工维护成本，不是增加记忆数量。
- 完整方向包括发现、审批、投递、复核与退出，但不要求一次全部实现。
- 自动发现与运行时投递分别接受验证；任何一项失败，都不拖累其余部分。
- 门 A 已完成（2026-10-22）：FAIL，失败分支生效（I.11）；判定以实验开跑前冻结记录为准。
- 检查-0 已支持继续验证：存在 10 个跨会话复发规则组。
- 41 条是这些组中的历史实例，不等于 41 次已确认复发，也不保证六周产生 30 个有效候选。
- 本契约采纳 R18 与 R21；与归档版本冲突处，以本文明确列出的替换决定为准。

## I.2 终态愿景：稳定运行六至十二个月后

- 系统是一份小型、可解释、可撤销的用户经验集，而不是不断增长的聊天知识库。
- 每条生效规则都能回答：谁批准、依据什么、约束哪里、通过哪个渠道生效。
- 主模型正常工作时可以提交纠正候选，不需要先阅读全部历史问题。
- 用户没有新纠正时，系统基本保持安静；没有待审事项时，不要求完成例行仪式。
- 用户可以在纠正当下立即批准，也可以集中处理周度待审。
- 高频稳定约定逐渐减少重复解释；偶发问题不强求沉淀为长期规则。
- 无法靠提醒解决的问题，会退出记忆流程，转入工具、流程或人工处理。
- 成熟终态可以是"自动整理＋静态规则"，不以运行时引擎上线为成功标准。

### 用户一周的体验目标

- 稳定后希望每周只有约 0–5 个值得处理的待审事项；这是体验目标，不是预测。
- 初期按每周 5–10 个事项预留审阅负荷，包含误报与重复，不只计算真实纠正。
- 审批与整理目标控制在每周 5–10 分钟以内，并且少于被节省的纠错时间。
- 记忆主动 nudge 目标是每个符合授权范围的根会话 0–1 次，不追求多发。
- 若某周有 10 个符合范围的会话，记忆 nudge 可为 0–10 次；实际还受 L0 和额度限制。
- 复发改善应表现为：仍有类似任务时，用户不再反复解释同一条约定。
- 每周少一次高成本重复纠正可以很有价值，但不能用更多审批劳动换取表面改善。
- 不承诺固定下降百分比；零反馈、低活跃或没有适用任务，都不算证明有效。

## I.3 设计原则

机器管发现，人管判断；候选、确认发生与批准生效严格分离；热路径只执行确定性授权；效果必须回到真实用户纠正，不能由模型自报闭环自证；授权不因持久保存而扩大；所有投递有界、可见、可停；异常时不增加行为；遵循上游，只使用插件自有通道，不修改官方 prompt、skills 或预设；每增加一个机制，都必须证明它减少了用户的总负担；**（R21）本框架是 OpenCode 专用：规则与事件以用户所有的纯文本存于统一根 `~/.local/share/opencode-supervisor/memory/`（App 管理树同级，避免升级/重置清除 plugin 目录；在 agent 文件白名单之外，权威完整性不依赖目录名），单库＋scope 字段；思想可迁移到其他 harness，但不为换 harness 保留可移植层（Rule/Binding 分离、可移植范围键、harness 字段均撤销）；文档标注"备份这一个目录"。**

## I.4 三个概念，三种责任

- **问题：**值得关注的模式，可以尚未成立；机器提出，用户确认其含义。
- **事件：**一次有来源的反馈；机器记录，用户判断是否真是纠正、是否属于旧问题。
- **规则：**允许影响后续工作的约定；只有用户能批准其正文、范围和授权期限。
- 自动检查来源真实性，不等于自动确认语义正确。
- 真实用户消息也可能只是需求变化、引用或讨论，不能仅凭来源合格就计为已确认纠正。
- 主题只用于整理，不决定两个事件是否属于同一问题。
- 没有已知问题标识也允许上报；跨会话合并默认可在人审时完成。

## I.5 完整生命周期

| 环节 | 职责与决策者 |
|---|---|
| 发现 | 主模型识别明确用户纠正，或用户主动提交；机器可以建议，不保证找全。 |
| 候选 | 宿主校验来源、记录上下文并消除重复提交；机器不据此批准规则。 |
| 复核 | 用户确认、合并、丢弃或暂存；即时处理与周度处理使用同一待审入口。 |
| 起草 | 模型或用户将经验写成短规则；模型产物始终是草稿。 |
| 批准 | 用户批准最终正文、范围、期限和投递方式；批准问题不等于批准未见过的正文。 |
| 生效 | v1＝系统展示精确补丁与推荐目标，**用户手工应用**；批准成功不等于已落地。 |
| 效果观测 | 系统保留补丁与应用记录，复核期只读检查已批准正文在场、已停用正文离场；用户结合实际任务机会判断是否减少纠正。 |
| 复发待复核 | 新反馈只追加事件与待复核提示，不自动宣告规则无效。 |
| 重试 | 用户决定是否修改或再次试用；没有用户动作就不进入下一轮。 |
| 升级处理 | 用户决定转为工具修复、流程约束、项目文档或人工注意事项。 |
| 退化与停用 | 用户停用、缩小范围或不再续期；停用立即产生移除补丁并阻止再发布。 |
| 删除与退出 | 用户可删除规则或关闭模块；系统不从旧事件自动恢复被撤销的授权。 |

- 停用不会撤回已经进入上下文的内容，也不会回滚已经产生的代码；库中停用不等于所有副本已撤回。
- 需要清除残留影响时，应停用相关规则并开启新会话；其他文件副本的加载遵循宿主。
- 到期表示授权结束，不表示系统自动判断规则内容错误。

## I.6 人审与授权边界

- 默认进入待审队列，不因每次 report 或每次新会话自动弹出 question。
- 用户明确要求保存、修正或立即试用时，可以当场审批。
- 周度复核只处理新增事项和待复核事项，不要求每周重审整个规则集。
- 不重复催问同一个未处理问题；队列拥堵时宁可暂停自动新增，也不制造更多通知。
- 审批必须展示最终正文、项目／目录边界、适用 agent 及授权期限。
- "仅本会话试用"只对指定会话和 agent 有效，保存记录不意味着下次自动启用。
- 长期生效必须获得明确的长期授权，不从一次会话选择推断。
- **（R21-B1）v1 静态生效的诚实边界：**期限是 digest 里的复查日期，不做自动过期；仅本会话、单 agent 限定的规则 v1 不发布（静态文件无法表达该边界），保持未发布状态。
- 项目身份（project_id）与发布目录边界是两回事；审批展示规则将实际静态加载的范围，不能兑现的范围承诺不发布。
- 项目使用宿主稳定标识；目录边界必须可由宿主确认，不能由模型随意扩大。
- agent 限定是适用范围，不是概率降权依据。
- 模型可以代为展示审批问题，但真实授权必须由宿主可靠确认。
- 没有问、没有回答、回答含糊、正文被改动，均不得视为批准。
- **（R21-C6）可信审批面**：宿主确认的用户操作（用户在 digest 界面的亲自操作，或用户本人键入的命令）；决策记录保存展示正文＋边界＋目标的哈希。模型写入 `approved`、摘要中出现 approve、或存在 git commit，均不构成批准。
- 若原生 question 无法提供可信授权依据，就使用现有人审入口，不增加代理审批协议。

## I.7 与 supervisor、宿主及上游的边界

- supervisor 负责来源检查、候选保存、授权执行、额度及可见记录。
- 主模型负责发现和起草，不拥有批准、自动停用或自动重启规则的权限。
- 现有 L0 确定性规则继续运行，不依赖记忆模块才能生效。
- L1 语义报告只产生候选，报告次数不能把它升级为 L0 事实。
- 所有主动运行时提醒复用现有 nudge 单出口，不另建旁路注入。
- L0 与记忆共享现有每会话最多三次、1200 字符的额度口径，L0 优先。
- 1200 字符沿用现行配置的计量范围，不在新设计中重新解释。
- agent 切换、规则改版、重复调用工具，都不重置会话额度。
- 预算不足就不发；不能截断或自动改写已批准正文来挤进预算。
- 计划发送与实际送达分开记录，未送达不能被评价为提醒失败。
- 不承诺全部请求持续可见；每个请求重新追加不能伪装成一次投递。
- 只接入根会话；宿主钩子覆盖子会话，不构成扩展子会话的理由。
- **（R21）中央库保存授权与全部历史（统一根，见 II.1）；AGENTS.md 段落是静态发布结果，不是第二份规则权威。多设备沿用访问同一服务端状态；别处的第二份库不支持、不合并。**
- 不持久化全部 hook；只保留复核必要的证据，原始对话仍由宿主管理。
- 宿主权限与危险操作确认继续独立存在，记忆不能替代安全控制。

## I.8 静态文件与生效方式：同一经验，不双重生效（R21 修订）

**总则：中央库＝授权权威；静态文件＝发布结果；同一条规则只有一个主动生效通道，不双写、不双发；已静态发布的规则不再经 nudge 或任何查询回送。**

### v1 生效方式：补丁-人贴（用户裁决 2026-10-22）

- 批准后系统展示**精确补丁**（含推荐目标与边界说明），用户手工应用到目标文件；插件零文件写入。
- 复核期做**只读检查**：已批准正文在场、已停用正文离场；发现漂移只报告差异，不自动改写。
- 目标规则（R21-B2）：只建议**已存在且用户确认过的文件**，永不创建新文件（含"项目只有 CLAUDE.md 时不新建 AGENTS.md"）；默认 git 未跟踪目标（全局 `~/.config/opencode/AGENTS.md` 或 gitignored 文件）；跟踪文件须在决策记录中显式确认（个人批准不自动成为团队政策，发布会出现在 diff、提交与协作者面前）；规则加载范围不得宽于批准范围（子目录规则不进根 AGENTS.md）。
- 跟踪文件被外部改变（pull/merge/checkout）视为"目标已变更"，送人审处置；不解释为"用户删除正文"。
- 手写段落始终由用户维护，永不自动覆盖；补丁段落只来自有效人审决策。
- 修改已发布规则：旧正文留任，直到新版本被批准并由用户应用。
- 规模限制沿用 v2.0（受管段落 ≤10 行、段外零写思路）；超限时整体失败提示，不截断。

### v1 已知限制（诚实声明，R21-B1）

- 静态规则不自动过期：期限＝digest 复查日期。
- 仅本会话、单 agent 限定的规则不发布。
- `query_memory` 在 v1 移除：没有允许返回的内容（静态规则在文件里，运行时规则不存在）。
- 不承诺任意 worktree 副本同步、到期即时撤回、按 agent/session 精确过滤；不适合静态表达范围的规则保持未发布。

### 升级路径：自动发布受管段落（Oracle R21 完整契约）

实测每周贴补丁分钟数证明值得时，才升级为插件自动发布；届时必须实现：原子写（临时文件+rename）后记录结果；发布前与上次结果做**空白规范化后**的 diff，手改/删行/marker 异常即停止写入并展示差异；被删除的行不自动补回（恢复/采纳手改/重新发布都回到人审）；停用立即阻止再发布并从已知目标移除，清理失败必须上报"尚有静态残留"；恢复旧备份（含 git checkout 库）不自动触发重新发布。

- 运行时规则（若门 B 通过）以其已批准授权为准，不再同时写入静态文件。
- 切换通道需要用户确认，不能先复制启用，再期待以后清理旧副本。
- 静态文件只承载适合其正常加载范围的约定。
- 门 B 决定运行时方式是否值得增加；平局或证据不足时选择更简单的静态方式。

## I.9 效果观测与停止

- 核心观察对象是用户再次纠正同类行为的窗口，以及为维护系统花费的时间。
- report 成功率、规则数量、查询次数和注入次数都只是运行指标，不是收益指标。
- 效果复核可以直接查看宿主真实对话，不能只看模型成功上报的队列。
- 未再次报告，不等于未再次发生；用户不再使用该任务，也不等于规则奏效。
- 评价时同时看是否实际遇到适用任务，不能只比较不同活跃程度下的原始次数。
- 新问题若明显由提醒诱发，也计入负面结果，不因难建立关联而忽略。
- 用户纠正是错误证据，但不能单独区分未送达、未遵守、归类错误或规则错误。
- 对原因不清的复发保留待审，不自动处罚规则。
- 严重副作用、授权越界或安全异常发生时，先阻止继续投递，再由用户决定规则去留。
- 若用户持续认为直接维护项目文件更省事，这就是充分的收缩理由。

### M0：门 A——已完成：FAIL（2026-10-22）

- 失败出口：停止自动发现路线，采用手动入口与人审静态规则。

### M1：候选队列与人审，不上线运行时注入

- 建什么：候选登记、来源查看、人工合并，以及周度和按需即时复核。
- 测什么：真实误报、重复负担、漏记体验，以及每周处理时间。
- 轻量整理标注（R20 保留、R21 降级）：每条 Issue 标注 preference/capability、global/project、关联模型；记录**手动入口整理增量**（用户不借助系统是否会想起该候选）。
- 继续条件：相对用户直接整理纠正，实际省事，且待审不持续积压。
- 停止条件：审核经常超过时间预算、候选大多无用，或用户更愿意手动记录。
- 失败出口：关闭自动新增，保留手动入口、已整理问题和用户批准的内容。
- 独立价值：即使没有任何新投递机制，也减少寻找和整理纠正的工作。

### M2：少量规则与门 B

- 建什么：由用户批准少量范围明确的规则，比较静态基线与有界运行时候选。
- 测什么：是否减少需要用户纠正的行为，是否新增错误，以及上下文和维护成本。
- 继续条件：运行时方式表现出值得额外复杂度的收益，标准在开跑前冻结；成本项计入 OpenCode 升级兼容、发布/补丁维护与审阅成本（R21 替换原"适配器重移植成本"）——平局更倾向静态。
- 无环境快照时只判断识别和选择，不把模型承诺修改计为修复成功。
- 失败出口：运行时不占优就保留静态；两者均无价值就不投递这些规则。
- 独立价值：确定经验应该放在哪里，而不是先建引擎再寻找用途。

### M3：选定通道的有限真实试用

- 建什么：只实现门 B 支持的通道、授权边界、送达记录和停止入口。
- 测什么：真实任务中的复发、误投递、审阅负担与副作用。
- 默认六周作为复核点，不把六周解释为必然拥有足够样本。
- 继续条件：存在实际适用机会，用户体验与维护成本支持保留。
- 失败出口：停用问题规则或回退静态；机会不足则暂停扩展，不强行判成功。
- 独立价值：少量已验证规则开始替用户减少重复解释。

### M4：长期稳定运行

- 建什么：只补足已经暴露的维护缺口，不把愿景中的选项全部实现。
- 测什么：几个月后是否仍省事，规则是否过时，是否逐渐变成第二份项目配置负担。
- 继续条件：经验集保持小而可理解，用户愿意保留，收益没有被治理成本吃掉。
- 退出路径：随时缩减到静态文件或纯手工维护；已批准知识仍归用户所有。
- 终态没有必须达到的规则数、自动化率或注入次数。

## I.11 门 A 两分支：其余设计如何幸存

- **适用范围：**门 A/B 结论仅对受测 harness（OpenCode v2）与模型（glm-5.3）有效；切换 harness/模型后，自动发现回落为手动入口，不静默假装仍然成立。

### 通过：自动发现进入 M1（未发生）

- 通过只授予自动提交候选的资格，不授予自动确认、批准或生效的权限。
- 误报可能仍显著，先观察候选队列负担，不直接把每条 report 变成 question。
- 实验依赖了哪些历史目录或提示，生产结论就只覆盖那些条件，不能扩大解释。
- M1 证明省事后，再进入门 B；自动发现与投递收益分别成立。

### 失败：静态规则＋手动入口成为正式终态候选（现行分支）

- 用户通过"记住这次纠正"主动提交，后续复核、批准、停用流程仍然成立。
- 继承 v2.0 的人审静态落点；**不继承其"AGENTS.md 是唯一权威"与"自由编辑、自动容忍覆盖"语义（R21：中央库＝权威，见 I.8）**；也不自动恢复旧版固定句式和后台蒸馏流水线。
- 生命周期、授权边界、外部校验和退出机制全部保留，不需要推翻总体设计。
- 不为挽救失败路线临时加入后台分类器、更多提示或反复催促。
- 未来只有出现新的可靠能力或明确需求，才另开验证；不反复调到旧测试集通过。

## I.12 明确不做

- **关键词激活引擎：**replay-27 未过预登记阈值，不以换词表的方式复活。
- **自动批准或晋升：**候选质量和发生次数都不能代替用户判断。
- **自动失效：**复发不等于规则错误，停用必须有人的判断。
- **自动刷新和续期：**被撤销的授权不能被一次新反馈恢复。
- **每会话自动弹问：**避免把使用助手变成维护记忆的前置任务。
- **全部请求常驻 nudge：**违背现有额度；静态文件加载不冒充运行时单次注入。
- **概率退化：**缺少可靠的适用机会分母和参数依据，初版只执行明确授权。
- **强制三次重试或强制换思路：**改写次数不是有效试验次数，正确规则也可能未被遵守。
- **旁路模型链：**不以更多模型角色弥补主模型发现能力尚未通过验证的问题。
- **未批准历史检索：**避免候选先进入上下文，再制造支持自己的新证据。
- **全量 hook 数据仓库：**持久化更多内容不等于获得更可靠的纠错判断。
- **在线 RCT 与标签基础设施：**当前量级先做有限验证，不建设长期实验平台。
- **子会话接入：**父子归因与共享额度尚不值得增加到首版。
- **防篡改密码学：**不在插件内另造安全系统，也不宣称能抵御同权限 agent 主动改写。
- **跨项目自动泛化：**相似主题不代表规则具有相同适用范围。
- **双写静态与运行时：**避免重复注入、授权分裂和删除后复活。
- **门 A/B 失败后照常上线：**失败出口是正式产品选择，不是待绕过的障碍。
- **（R21）自动采纳人工编辑：**用户手改已发布正文不触发任何自动写入；"采纳手改"＝新版本＋新决策记录。
- **（R21）自动创建目标文件 / 默认发布到 git 跟踪文件：**见 I.8 目标规则。

## I.13 开放问题与未来选项

- **便宜的 L1 分诊：**只有审阅负担成为实测瓶颈、且有新能力证据时才验证；只分诊，不审批。
- **流程摩擦来源：**工具失败、派发被拒可另列线索，但不得伪装成真实用户纠正。
- **接入摩擦线索的条件：**来源可核验、故障可复现、确有重复维护成本，并与现有纠正指标分开。
- **摩擦的优先出口：**能修工具契约或流程，就优先修基础设施，不把稳定 bug 变成永久提醒。
- **跨设备：**同一用户访问服务端同一份状态，不新增同步冲突体系。
- **团队共享：**需要另行解决批准权、适用对象与隐私，个人批准不自动成为团队政策。
- **跨项目复用：**用户可以明确复制或扩大范围，系统只建议，不自动迁移。
- **与 `/reflect` 分工：**若使用该能力，它负责主动回顾和提出草稿，不获得批量生效权限。
- **与手写 AGENTS.md 分工：**稳定项目约定由用户维护；系统主要减少发现、整理和复核成本。
- **真权限隔离：**若未来要求抵御恶意同权限 agent，交给宿主级权限边界，不声称当前方案已覆盖。

# Part II. 现行细节契约(与 Part I 冲突处以 Part I 为准)

## II.1 对象模型与存储（R21 重写）

| 对象 | 含义 | 谁写 | 状态 |
|---|---|---|---|
| **Issue(问题候选)** | 需要关注什么: 一行描述 + 主题(导航用) + 创建证据 | 手动入口(候选) / 用户 | draft → approved → merged/dropped |
| **Event(事件)** | 何时、依据哪条真实证据再次发生 | 手动入口(候选, 幂等) | 待确认 → 确认 / 误报 |
| **Rule(已批准规则)** | 单记录: 正文+版本 / scope+目录边界 / 授权范围+期限(复查日期) / 投递通道+批准的目标文件 / 审批引用 / 最近发布结果 | **仅用户批准** | active → disabled(停用需人, 重启需人) |

- **统一根（单库+scope 字段, 不按项目分区）：**
```text
~/.local/share/opencode-supervisor/memory/
├── rules.json        # 当前规则、scope、授权引用、发布信息
├── issues.json       # 候选与人工整理状态
├── events.jsonl      # 有来源的纠正事件, 不收全量对话
├── decisions.jsonl   # 对具体版本的批准/否决/停用记录
├── projects.json     # 宿主项目 ID、人读别名、已确认目录关联
└── digest/           # 可重建的待审列表与差异视图(纯视图, 不进模型上下文)
```
- 不另造第二个 memory 根；不放进工作仓库；文档标注"备份这一个目录"。多设备＝同一服务端状态，不做同步/合并。
- rules.json 保存当前状态，decisions.jsonl 保存历史；**已撤销的 active 状态不得从旧批准记录自动重建**；人工重建必须重放全部决策日志（含停用）。
- **store 故障行为（R21-C2）：**库缺失或损坏 → fail-closed：不发布、不清理、提示"存在受管段落但无授权记录"；绝不自动重建。`rules.json` 并发写用锁或版本检查（多 OpenCode 实例共享服务端）。
- **git：**v1 不要求；用户可自行对统一根做本地 git。无自动 commit/push；git checkout 库视同恢复备份，不自动重发布；git 历史不证明批准。

### 作用域键（OpenCode 专用）

| 情况 | 键 |
|---|---|
| Git 项目 | `project:<宿主 project_id>`（不透明字符串；实测定格于初始化、幸存 rebase、归并 worktree，未验证跨大版本） |
| 人读名称/别名 | `projects.json` 登记（名称、已确认路径）；git remote 仅作导航信息，**永不作授权依据** |
| Worktree | 共享宿主项目身份；**共享身份≠自动向所有 worktree 发布**——发布仍须符合用户批准的目录/文件边界 |
| 非 Git 稳定目录 | `directory:<canonical-path>`（宿主确认的规范绝对路径） |
| 临时聊天目录 | 仅保存候选；不自动赋予长期目录授权，更不回落为全局 |
| 用户全局 | 显式 `user-global`（此用户 OpenCode 环境的跨项目授权），不是 `*` 兜底 |

- 三不变量：①**身份失效不得扩大范围**——ID 缺失/冲突/宿主重建后改变 → 停止关联，用户显式重绑定，不按同 remote 自动接回；②宿主的非 Git "global" 身份 ≠ 用户批准的 user-global；③project_id 是登记与匹配键，**不是安全隔离边界**。
- **新目录未确认（R21-C3）：**由共享 git 历史（fork/模板克隆）得到同一 project_id 的新目录，在用户于 projects.json 确认前保持未关联。
- **来源范围与生效范围分离：**某项目的真实纠正可经人审形成 user-global 规则，但 Event 永远保留原项目/目录来源；不放宽手动入口的同项目证据要求。

### 证据与溯源（R20 保留项, 减量）

- **证据快照：**Event 存短摘录+时间戳+来源消息引用（宿主清理历史后仍可理解）；摘录不替代最初的真实性校验。
- **观测模型标识：**解释证据、提示人工复核；不据此自动停用。preference/capability 分类保留为轻量复核信息，无自动衰减。
- **宿主赋值, 不信模型传参：**project/session/agent 由 hook 上下文注入，模型参数仅作描述性字段。
- 主题只作导航聚类；去重与合并由用户在复核中处理。同一来源事件幂等。
- **证据来源宿主强制：**evidence 引用必须是同项目内真实存在的用户消息 ID，宿主直接拒绝其他一切来源。

## II.2 工具面（R21 修订：手动入口模式）

1. `report_correction`: 上报一次用户纠正（v1 由用户主动触发——对话指示或命令入口；自动发现待门 A 重试）。参数: 描述/主题/evidence(真实用户消息引用, 宿主校验)/可选 issueId(宿主确认过存在且同项目时记为复发; 无则新建候选)。**返回仅 ack + ID, 不返回任何历史**。
2. ~~`query_memory`~~: **v1 移除**（R21-B1）——静态规则在文件中生效，运行时规则不存在，没有允许返回的内容。
- 工具描述明确: 允许不记录; 禁止把模型自评、工具返回、nudge 内容当作用户纠正; 无有效 evidence → 宿主直接拒绝调用。
- 工具对根会话可见; 首版拒绝子会话来源(宿主拒绝写入, 防根/子重复计数)。
- mock 回执支持(验证期不写生产存储)。

## II.3 触发流

```
report_correction(幂等, 宿主校验 evidence)
  → ① 新建 Issue 候选 或 追加 Event + 关联计数(仅此为自动)
  → ② 返回 ack + ID(无历史, 无注入)
  → ③ 规则文本起草发生在复核时(人审界面), 不在任务会话内注入草稿
  → ④ 用户复核(即时或周度, Part I.6): 合并/丢弃/批准
  → ⑤ 批准 → 系统展示精确补丁+推荐目标(遵守 I.8 目标规则) → 用户手工应用
  → ⑥ 复核期只读检查: 已批准在场/已停用离场; 漂移只报告不改写
  无任何环节自动改 Rule 状态; 无旁路模型链; 插件零文件写入(v1)
```

- 停用/否决优先: 用户停用的规则, 事件再多次也不复活。
- 复发只追加事件+待复核标记(Part I.5), 不存在"消失→复发→自动刷新"通道。

## III.0 设计哲学修订: 模型自主编排 + 宿主约束权限

- 三分法按**功能**而非按"要不要删": ①决策方法处方(教模型怎么做)——应删, 是强模型天花板; ②机制约束(物理不变量, 如 fail-closed/单出口/预算)——留, 能力双向放大不改变其价值; ③用户政策(何时自动记录/投递)——留, 是授权问题非能力问题。
- "仅用户要求才记录"拆两层: **能力层**(模型可随时选择调用记录工具)与**政策层**(自动保存候选需用户显式开启 + 有界待审队列)。自动记录非零副作用(候选噪声挤占 digest), 故政策默认手动。
- **"不阻碍能力增长"必须可检验**: 落为 lint——工具描述中每一句必须是三者之一: 宿主可核查的效果/契约陈述、或标注"可删提示"的文案。纯散文式边界(无任何机制检查)按 bug 处理。**v6.3 分工细化(R33)**: 描述=用途+必要调用条件+实际效果(一两句, 含关键"不做什么"); schema=输入(类型/必填/上限); 返回值=具体失败与下一步。删除工作流教程, 不删权限语义。
- **规则分类同样适用于已存储规则**(R25 Q1): preference 类=用户政策, 保留; capability 类=针对当前模型弱点的处方, **模型换代时人工复核**, 不自动禁用也不永久免检。
- **插件身份定调(R28-claude, 2026-10-23)**: supervisor = **人治理的政策插件**(capture→人审→静态规则→可选确定性检查→复发度量, 一个环), 不再自称"旁路观察者"。带内/带外不是本质分界, **产出的寿命与批准权**才是: bcp=模型自管的工作记忆; supervisor-memory=人批准的持久政策。存储可共享, 批准权不混。

## III.2 确认协议(v6.3: 桥 A 宿主 form, R33+桥裁决定案, 已实施)

> v6.2 的"短码+真人后续消息"方案被 R33 明确修订: **宿主原生确认的可信应答可替代短码**。探针(/tmp/opencode/q-bridge/)证实 execute 调用栈内无 ctx.question API, 但宿主 form/question HTTP API(桥 A)与 ctx.permission.assert(桥 B)两条实测可用; 裁决**选桥 A 单用**。

**桥 A 机制**: 插件在工具 execute 内作为 **loopback HTTP 客户端**调用宿主既有服务(端口/凭据取自宿主 service.json; 插件零监听零新端口), 创建单选 form(选项=Confirm/Cancel, custom:false), 阻塞等待应答, 应答直接回插件——**不经过模型**。UI 侧与原生 question 同体系(TUI 已实测; 手机渲染待真人验收)。

**协议要素(全部已实施, test/approval.test.mjs)**:
1. **完整展示在先**: 全文正文(非摘要)/scope/agent 限定/channel/静态目标绝对路径与跟踪状态/review date/对象哈希/撤销边界/"持续注入非仅本会话"(投递类)/真实截止时间; 正文作审阅数据展示(Markdown 不得冒充按钮)。
2. **红线**: 模型不得提供 confirmed/答案/hash/"用户已同意"; 参数黑名单拒绝; 模型永远不当中继。
3. **deadline 语义**: 默认 10 分钟, 配置上限 30(confirmTimeoutMin); **检查先于每次读取且先于接受 answered**(关闭探针发现的迟答竞态); 到期→本地 pending 不可消费→DELETE form; DELETE 失败也不得接受迟答。取消/对象变更/fork→确认失效; 重试=全新决策。
4. **单次消费**: 一个 formID 只能喂一个 decision(consume-once)。
5. **审计链**: approval-audit.jsonl 记 `decisionId ↔ (sessionID, formID) ↔ 对象版本+展示快照哈希+回答+时间+截止+消费状态`; 拿不到宿主 formID 关联→不批准→CLI 回退; 不得自造 id 补证。
6. **同 UID 剩余风险声明**: form 应答不抵抗同 UID 冒充(loopback 直答), 与 AGENTS.md 直写同级——已接受; 但**不得声称证明真人身份**; HTTP 冒答还能伪装审计, 故审计只作检测补充不作授权依据。
7. **桥 B 弃用原因**: 二元展示弱/assert 未返回审计 ID/saved(always)权限可能静默通过; 若未来启用须强制每次实际询问+仅 once+不持久化。
8. **TOCTOU 修复(bug①)**: 共享审批服务层跨进程短临界区(approval.lock O_EXCL, 死 pid/心跳恢复)包住"终态复核+recordDecision"; 等用户时绝不持锁; CLI 与工具同一入口。
9. **CLI 定位**: init/诊断/导出/无模型停止入口 + 桥不可用时的备用审批(三段式保留, 底层同临界层); 不经 --yes 变成免确认通道。

## III.8 运行时投递通道契约(step 3, v6.2: R31+R32 判决定案, system-ride 形态)

定位: 已批准规则的 **project×agent 有界投递**。只投递、不检测(§III.7 维持关闭); 存在理由=AGENTS.md 静态通道按目录加载、结构性无法按 agent 限定。**形态=system prompt 骑乘**(探针 /tmp/opencode/probe-system/ 实测: v2.1.2 context hook 的 event.system 为 Array<{type,text}>, 可变且生效于全部上游请求, 宿主每请求重建, 子会话同样触发): 匹配规则的正文在**每次模型请求**时幂等追加到 system 数组尾——会话内常驻、抗压缩、重启失效即重注、零投递状态机。v6.1 的消息投递机器(持久化去重/先写后投/信封打包/轮转/预算让位)全部废弃。

**匹配门(deliver 匹配器, 全部确定性, fail-closed)**:
1. 规则 approved 且 delivery-enabled 且 `channel == system-ride`(通道枚举 = static-agents-md | system-ride; 一条规则一个通道);
2. 会话范围: v1 默认仅根会话; **明确获批的子代理**可开通(子会话验证自身 project/agent, 不继承父授权; 只开放规则读取注入, L0 黑名单与审批权限不变);
3. project 匹配: `session.project_id == rule.scope.projectId`(user-global 规则不限项目);
4. agent 匹配: 宿主提供的**当前请求 agent 名**与 `rule.agents[0]` 字面相等; `agents` 空=不限 agent; agent 名未知/缺失→拒投; 改名后旧绑定静默停投(不自动重绑), 由 digest 哨兵行暴露。

**投递形态与限额**:
- 每次 context hook 把全部匹配规则按**固定顺序**(规则批准时间)整条装入: 头 `[supervisor-memory:rule:<id>:v<version>]` + 正文;
- **每请求总额 ≤1200 字符(含标头)**: 依固定顺序装入, 装不下的整条跳过并记日志+列入 digest, 绝不截断, **不轮转**(持续溢出=人裁剪规则的信号);
- **只 push, 绝不改写既有 system 元素**;
- **请求内防重**: 同一请求内 hook 多次调用只注一次(宿主每请求重建 system ≠ push 幂等, 须请求内护栏);
- 形状防御: system 非预期形状(非数组/元素非 {type,text})→**仅关闭 memory 注入**(插件其余功能不受影响), 宿主升级后重跑探针再恢复。

**授权语义**: 新决定种类 `delivery-enable` / `delivery-disable`, 绑定 **(ruleId, version, bodyHash, channel)**; 改版重批准→投递自动复位 disabled; **常驻性与 system 指令优先级变化属显式批准语义**(批准对象须载明"将随该会话每次模型请求注入 system"); 会话授权(1b)须绑 sessionId; 跨会话启用另行确认, 旧授权不自动扩大。v6.3: 授权入口=`memory_enable_delivery` 工具(桥 A 确认, 见 III.2)与 CLI 双入口, 同一临界层; **投递门、四元组绑定、预算、撤销语义不变**。
