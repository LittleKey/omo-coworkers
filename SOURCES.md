## 当前包权威与溯源记录 (`v6.1.0` OMO 原生配置管理器升级、独立模板族与独立行为设置, 2026-11-26; `v6.0.0` OMO 原生配置交付迁入与旧 `dotfiles/opencode` 写入链退役交接, 2026-11-26; `v5.0.0` supervisor 移除, 2026-11-25; `v4.0.0` OpenChamber 扩展重构, 2026-11-18)

- **当前随包发布载荷（`package.json` `files`: `openchamber`, `skills`, `plugins`, `README.md`, `INSTALL.md`, `SOURCES.md`, `LICENSE`）**：
  - **OMO 原生配置管理器核心（`openchamber/native-config/manager.mjs`）**：
    - 自动发现并读取默认候选配置根（`$XDG_CONFIG_HOME/opencode` 或 `~/.config/opencode`）下的 `oh-my-opencode-slim.jsonc` / `oh-my-opencode-slim.json`（`.jsonc` 与 `.json` 并存时按原生优先级选用 `.jsonc` 并返回 `SHADOWED` 诊断，不再整库锁定）及受管提示词资源。
    - 执行服务端保守字段分类投影：普通字段（`ordinary`）返回真实值；提示词字段（`prompt`）与受保护字段（`protected`，基于启发式规则识别已知敏感键名 `env`/`headers`/`authorization`/`apiKey`/`token`/`secret`/`password`/`credentials`/`provider`/`mcpServers`、已知凭据/令牌特征值如 `{env:...}`、`Bearer`/`Basic`、`-----BEGIN`、`sk-`/`ghp_`/`github_pat_`/`xox*-`、含内嵌凭据的 URL 或查询参数，以及未在 `openchamber/native-config/schema/omo-3.0.8.json` 与 `contextKnown` 中同时登记的 schema 分支）仅返回 `{ "protected": true, "placeholder": "<hash>" }` 占位符，不向浏览器发送原始 JSONC 全文或注释（注：启发式规则无法识别被伪装成普通文本并写入普通可编辑字段的任意自定义秘密）。
    - `POST /reveal` 仅在有效快照中授权提示词揭露；普通编辑、配方、用户模板及撤销先预览并统一 `PATCH /config`。前后存在标志独立于内容是否揭露；未经揭露的个人提示词仅显示摘要，公开配方目标可显示。揭露授权不持久化。

  - **内置和用户配方（`openchamber/native-config/templates.mjs`、`recipe-intents.mjs`）**：五族为 `document-role`、`lark-role`、`collaboration`、`claude-acp-guidance`、`antigravity-acp-guidance`。完全匹配返回 `NO_CHANGES`，不建立收据；不同个人值需逐身份显式选择替换。角色继承只接受 `session` 或 `orchestrator`，不要求同名 agent，不覆盖个人模型。

## Historical Provenance (`1.x`–`3.3.0` installer era)

This repository was assembled on 2026-09-19 from the maintainer's live OpenCode configuration, resynced on 2026-09-25 after a live "promptopt" rewrite (prompts, agent descriptions/orchestrator prompts, skill grants; `document-review-evidence` deleted upstream), and resynced on 2026-09-26 after live updates: `document-writer.md` restructured into Shared/WRITE/REVIEW with a full review contract, `oracle_append.md` and `orchestrator_append.md` extended (board review records, SHA-256 binding, rereview dispositions, fresh-session rule, user-facing synthesis), new `fixer_append.md`, and the live config's `document-writer` `description`/`orchestratorPrompt` rewritten, and resynced on 2026-09-27 after live updates that at that time removed the single-corrective-round budget, and resynced on 2026-09-30 after the orchestration rework: the review budget in `orchestrator_append.md` is now **one initial review plus at most two rereviews per review objective, counted across sessions** (superseding the 2026-09-27 unlimited-rounds description), `prompts/lark-operator.md` is now sourced from the host's native agent definition with its frontmatter stripped, the four skills previously recorded as having no local source are located in the maintainer's project-scoped skill directory (still unpackaged, see "Not vendored"), and the overlay gained an `agents.oracle` permission block keeping Oracle review read-only (see "Overlay design"). A same-day **2.0.0 dual-host rework** then rebuilt the package as an installed product: `bin/dw-install.mjs` + `installer/` (host-aware additive installer for v1 ≥ 1.18.29 within major 1 / v2 ≥ 2.0.20 within major 2 with manifest, uninstall, rollback), the two roles now install as **host-native agent files** with per-host permission vocabulary (prompt authority = `prompts/<role>.md`, verbatim), and the overlay was slimmed to exactly the two managed agent entries — the `agents.oracle` block and the `agents.orchestrator.skills_remove` guardrails are **personal deployment configuration** and stay in the owner's dotfiles, not in the generic package. Copied items are byte-identical verbatim copies (`diff -r` verified); generated items are listed with their derivation. Statements about omo-slim behavior were verified against the installed oh-my-opencode-slim **2.2.21** source (`dist/index.js`, `oh-my-opencode-slim.schema.json` in the OpenCode plugin cache), re-checked against **2.2.25**, and the dual-entry/v2 behavior against **3.0.1** sources and a real isolated **2.0.20** host (2026-09-30). Resynced on 2026-10-06 with the maintainer's phase-1 upstream-default restoration — an isolated candidate, not yet synced to the live configuration: `prompts/council_append.md` and `prompts/fixer_append.md` were retired and are no longer shipped, `explorer_append.md` and `designer_append.md` were added, and `orchestrator_append.md`, `oracle_append.md` and `librarian_append.md` were reduced to minimal increments on the upstream builtin role prompts (oh-my-opencode-slim 3.0.1 defaults; no builtin role body is packaged). The five appends were mirrored byte-identically from the isolated phase-1 work copy (see the note under "Copied verbatim") and remain under refinement, so no exact byte counts are recorded; the only overlay change was removing one leftover Council-dispatch sentence from `agents["lark-operator"].orchestratorPrompt`. This resync carries no runtime behavior validation, and the oh-my-opencode-slim **3.0.2** port is planned but not completed.

## Overlay design (syntax verified against omo-slim 2.2.21 source; re-checked against 2.2.25 and the 3.0.1 sources, 2026-09-30)

- **Two managed entries only (2.0.0)** — the installer owns exactly `agents["document-writer"]` and `agents["lark-operator"]`; every other semantic value of the target's overlay file is preserved through the structured merge (the merged file is re-serialized 2-space JSON, so original byte layout is not preserved). The overlay carries no `prompt`/system text: the effective prompt for each role is the host-native agent file the installer writes (v1 `agent/<name>.md` with a grouped `permission` map; v2 `agents/<name>.md` with an ordered `permissions` array using the 2.0 action names — `task`→`subagent`, `bash`→`shell`), body byte-identical to `prompts/<role>.md`. Observed effective on 1.18.33 (`debug agent`) and 2.0.20 (`/api/agent`, isolated host, zero model requests) in checks that ran without the OMO plugin loaded — combined native+OMO precedence is owner-validated separately. Builtin-role appends belong to dotfiles and are not included in this package or its installer payload.
- **`inheritModelFrom: "session"`** on both custom agents — enum `session | orchestrator` per the 2.2.21 schema; the resolver deletes the agent's model so it inherits the session/primary model (`dist/index.js` model-inheritance code; re-checked in 3.0.1). No model IDs are pinned; a fresh target instantiates the agents without model errors. A custom agent entry lacking both `model` and `inheritModelFrom` is skipped with a warning, so keep the field when reconciling.
- **Personal guardrails are not carried (2.0.0)** — the earlier portable `agents.oracle` read-only block and the 32-name `agents.orchestrator.skills_remove` list were owner-side deployment policy; they now live only in the owner's dotfiles configuration. The generic package ships no entries touching upstream agents (`oracle`, `orchestrator`, `council`, `fixer`) — nothing to force-overwrite, nothing to reset.
- **Layer array semantics** — config layers merge with wholesale array replacement (`skills`, `skills_add`, `skills_remove` never concatenate across user→project or preset→`agents`): the effective value of each directive key is the highest-priority layer's array, and an empty array shadows lower layers like any other value. Post-install grant procedures (INSTALL §6) therefore append only their entries to the effective pre-install winning array and never union shadowed lower-priority values; `skills_add` cannot re-enable a skill excluded via `"!"` tokens or `skills_remove`.
- **`agents.document-writer.skills` reduced from live** — the live 2026-09-26 config grants the writer the Lark body-editing set (`lark-doc`, `lark-markdown`, `lark-sheets`, `lark-base`, `lark-slides`, `lark-drive`, `lark-wiki`, `lark-whiteboard`, `lark-shared`) plus `yogo-products`; this overlay keeps only the three bundled grants (`maintaining-product-engineering-docs`, `domain-modeling`, `humanizer`). The Lark set is re-granted on targets only via the explicit opt-in in INSTALL §6; `yogo-products` is excluded by policy.
- **`$schema` stays `@latest`** — the reviewed live config pins the 2.2.25 schema, while the portable overlay retains its existing editor-schema URL. That URL is not a compatibility guarantee for future plugin versions; the tested versions and scope are listed below.
- **No `preset`/`presets`, no `model`/`variant`, no MCP grants, no `council`** — the live config's preset members, provider model IDs (`openai/*`, `newapi/*`), council endpoints, and MCP grants (`gh_grep`, `context7`) are environment-specific and are excluded; both custom agents carry `"mcps": []`, which grants nothing. Per-agent permission denials for `gh_grep_*`/`context7_*` are preserved verbatim.
- **No `lark-*` skills vendored; `lark-operator` ships `"skills": []`** — its Lark capability is populated on the target only from skills discovered after an official `lark-cli` install/update, each vetted for role fit, stated prerequisites, available CLI/auth, and least-privilege boundaries before granting (INSTALL §6). `lark-openapi-explorer` is never grantable to an agent denying WebFetch: it stays ungranted with the limitation recorded, and permissions are never widened or shell-bypassed to make a skill fit (the same vetting governs other cloud-document CLIs, INSTALL §6). Formal Lark document-body editing routes to `document-writer` only under explicit user opt-in with compatible granted skills (INSTALL §6); the writer's result contract (content location plus retrievable revision or retained snapshot and hash) applies, with Oracle review when requested or impact-gated; without the opt-in it is unavailable and never routed through `lark-operator`, which remains forbidden from formal document bodies. The formerly vendored `lark-openapi-explorer` copy was removed with the rest of the `lark-*` set.
- **Config-layer facts documented in INSTALL.md**, verified in `dist/index.js`: user plugin config = first existing `oh-my-opencode-slim.jsonc`/`.json` (`.jsonc` preferred within a dir) across the custom dir (`$OPENCODE_CONFIG_DIR`) and the default dir (`$XDG_CONFIG_HOME/opencode` else `~/.config/opencode`), searched custom-first — a custom dir with no plugin config falls through to the default dir; project config at `.opencode/oh-my-opencode-slim[.jsonc|.json]` merges over user (scalars override, `agents`/`presets` deep-merge); `OH_MY_OPENCODE_SLIM_PRESET` overrides the `preset` key; prompts resolve first-match-winner in the order project preset-dir → project base dir → custom-dir preset-dir → default-dir preset-dir → custom-dir base dir → default-dir base dir, and `agents.<name>.prompt` inline keys override the `<name>.md` file prompt (warning only; `<name>_append.md` still appended).

## Global install run (2026-10-15)

- **Feature under record (`--global` user-level install mode; v3.3.0 code, uncommitted at recording time)**: implemented and fixture-tested — 61 tests: 59 pass, 0 fail, 2 env-gated skips. CLI: `coworkers-install install|plan|verify|uninstall|rollback --global [--config-dir <dir>] [--force]`; `--global` is mutually exclusive with `--target` (exit 1); `--config-dir` (only valid with `--global`) defaults to `$OPENCODE_CONFIG_DIR` or `~/.config/opencode`. Mapping, config-dir-relative: prompt bodies → `oh-my-opencode-slim/<role>.md` (verbatim repo prompts); the three skills → `skills/<name>/` (plural, host-native); overlay → `oh-my-opencode-slim.json` — created wholesale if absent, additively merged if present without managed agent keys, and **preserved completely untouched (even with `--force`)** with a recorded notice when it already defines `document-writer`/`lark-operator`; manifest → `omo-coworkers-install.json` gaining `scope: "global" | "project"` (absent reads as project; schemaVersion stays 1) plus an advisory `notices[]` that `verify` re-surfaces; backups → `omo-coworkers-backup/<stamp>/`. Byte-identical pre-existing files/dirs are adopted (zero writes, hash recorded). The claude-advisor plugin is never installed in global mode: user-level auto-load needs an explicit `plugin` entry in the owner's `opencode.json`, personal config the installer never edits — the plugin stays project-scoped.
